## 성공 판정과 서버 응답 대조
- 성공 = **`applied:true` 이고 `eligible:true`** 인 응답만(`interpretRunResponse`). 서버 코드 확인: 실행 성공 응답은 `{ styleNo, applied: true, addedBomItemId, createdMaterial, ...judgement }`(`mapping-commit.service.ts:819`)이고 `judgement` 가 `eligible:true`·`message`·`outerRowIndex`·`info` 를 포함 → **둘 다 들어 있다**(e2e 도 `applied:true, eligible:true` 단언). 부적격은 `{ styleNo, applied:false, ...judgement }`(`:807`)로 `reason`·`message` 포함.
- 응답 래퍼: 서버 전역 `TransformInterceptor` 가 `{ data: … }` 로 감싸고, 프런트 axios 인터셉터가 `response.data.data` 를 이미 풀어 돌려준다(`axiosInstance.ts`). 새 API 함수는 `.data` 를 다시 꺼내지 않고 응답을 그대로 해석 함수에 넘긴다(이중 unwrap 없음). 서버 응답 본문 자체에는 `data` 키가 없어 인터셉터가 한 번만 벗긴다. 화면 단위 테스트는 풀린 응답 모양(서버 e2e 의 `res.body.data` 와 같은 필드)으로 작성됐다.
- 요청 본문: `{ styleNo, bomItems: style.bomItems }` — `commitMapping`/`bom-diff` 가 보내는 파서 출력과 같은 모양(별도 변환 없음). 보내는 필드(`id, category, itemName, consumption, requiredQty, colorOf, spec, composition`)는 모두 서버 `CommitBomItemDto` 필드에 있어 `forbidNonWhitelisted` 에 걸리지 않는다. 경로 `/mapping/outer-fabric-supplement/check`·`/mapping/outer-fabric-supplement` 는 서버 라우트와 같다.

## 실행 안전 규칙과 오류 처리
- 기본 선택 없음, 체크는 보충 가능 행에만, 확인 패널 문구("선택한 N개 스타일에 겉감 행을 1개씩 추가합니다. 스타일 정보·오더개요·선적일·계약·기존 자재 행은 바뀌지 않습니다. 계속할까요?") 후 **순차 한 번에 하나**(`runSupplementQueue`), 실행 중 모든 버튼·체크박스 잠금 + 내부 중복 실행 가드(`busyRef`), 성공(`보충 완료`) 스타일은 재선택·재전송 차단. 선택 0개면 실행 버튼 비활성. "처음에는 1개 스타일만 선택해 결과를 확인한 뒤 나머지를 진행하세요." 안내 있음.
- 오류 처리(사실대로): HTTP **5xx 가 연속 2회면 남은 스타일을 호출하지 않고 "실행하지 않음"**. 그 밖의 오류 — 시간 초과·네트워크·**400·401 등 4xx** — 는 그 스타일만 "실패"로 남기고 **다음 스타일로 계속**한다(연속 중단 규칙 없음). **401(로그인 만료)**: 프런트 axios 인터셉터가 토큰을 지우고 `/login` 으로 이동시켜 화면이 새로고침되므로 남은 큐는 사실상 끊기고, 이후 요청이 나가더라도 인증이 없어 서버가 거부해 **쓰기는 없다**. 다만 결과 화면은 사라지고(업로드 목록은 PR-237 보관으로 복원) 점검·실행 결과는 메모리라 다시 점검해야 한다 — 후속 후보로 "401 이면 즉시 중단"을 둘 수 있다.
- 서버는 실행 때 트랜잭션 안에서 다시 판정하므로(PR-258) 화면은 점검 결과를 믿지 않고 서버 응답만 본다.
