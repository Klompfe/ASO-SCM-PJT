## 작지 비교 화면 기본 "유지" 규칙 (프런트만)
- 전: `existingOnly` 이고 삭제 가능하면 기본 삭제. 후: 그 앞에 `keepByDefault` 이면 `keep`. `keepByDefault` 는 **기존 겉감 계열 행이 2줄 이상**일 때 그 "기존에만 있음" 겉감 계열 행에만 붙는 화면 전용 표시(서버 응답·저장 요청 모양 불변, 서버는 기본값을 정하지 않음).
- 조건은 비교 응답의 기존 행(bomItemId)만으로 계산한다. "제외"는 비교 요청의 **새 행**만 빼고, 응답에는 기존 행이 항상 전부 들어오므로 화면 조작으로 보호가 풀리지 않는다. 겉감 계열 1줄 이하 스타일은 이전과 동일, 겉감이 아닌 행의 기본 삭제도 그대로.
- 사용자가 직접 "삭제"로 바꾸면 기존 삭제 확인창, 수동 필요수량·확정 단가·종류 지정 체크, 발주 연결 보호(서버 재확인 포함)가 그대로 적용된다.
- 새 겉감 행의 선택지는 기존대로 "추가"뿐이며(서버에 "추가하지 않음" 값이 없음), 겉감 중복 상태에서 추가되면 저장 확인창이 반드시 뜬다.

## 알려진 한계
- **기존 겉감 1줄 + 새 인식 겉감 0줄이면 그 겉감 행이 기본 "삭제"다.** `origin/main`(이 PR 이전)의 `defaultExistingDecisionFor` 도 같다(`existingOnly && canDelete → delete`) — 이번 PR 이 만든 동작이 아니다. `소재` 단독 행도 이전부터 새 겉감이 없으면 "기존에만 있음 → 삭제"였으므로 **`소재` 인정 때문에 새로 이 위험에 들어오는 행은 없다**(오히려 새 겉감 1줄이면 이제 짝이 되어 삭제 후보에서 빠진다). 후속 PR-263 후보.
- 공존(`소재`+`겉감`) 스타일은 이전에는 `겉감` 단편이 짝(합치기)이 되었지만 이제 짝이 없어, 새 겉감을 확인하고 저장하면 겉감 계열이 3줄이 될 수 있다(삭제는 기본으로 일어나지 않고 확인창이 뜬다). **중복 행 정리 기능 없음.**
- 데이터 미보정, 클릭 동작 자동 테스트 없음(순수 함수·정적 렌더), 운영 DB 영향 건수는 확인하지 않음 — 배포 후 겉감 점검 탭 숫자(이전 55·17·17)로 확인.
