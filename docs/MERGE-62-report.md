## 겉감 짝 규칙과 서버 재검증
- 짝 판정 `findOuterFabricPair`: 기존 BOM 의 겉감 계열 행이 **정확히 1개**이고 새 인식 행의 겉감 계열도 **정확히 1개**일 때만 한 쌍(색상·규격·구분 표기 무관, 0개·2개 이상이면 없음). 겉감 계열 판정은 PR-256 의 서버 `isOuterFabricCategory`(PR-255 단어 경계 규칙, 안감·`INTERLINING`·부자재·`FABRIC` 제외)를 그대로 쓴다. 비교 API 가 아직 짝이 없는 그 둘을 `similar`+`outerFabricPair:true` 로 내려보낸다(이미 same 으로 맞았거나 다른 행과 짝지어진 행은 건드리지 않음).
- 서버 재검증(`mapping-commit.service.ts` 합치기 처리부): 대상 기존 행·들어온 행 중 **한쪽이라도 겉감 계열이고 두 구분이 다르면**, 이번 요청 이전의 기존 BOM 스냅샷과 이번 요청의 행으로 짝 조건을 다시 계산해 **둘 다 겉감 계열이고, 그 유일한 쌍(대상 행 id·들어온 행 인덱스가 일치)이 아니면 400, 전체 롤백**. 즉 (a) 임의의 다른 행을 짝으로 지정 거부, (b) 겉감↔안감·배색·부자재 합치기 거부. 구분이 완전히 같은 합치기와 겉감과 무관한 합치기는 기존 동작 그대로. 주의: 이 방어선은 **이전에 서버가 허용하던(화면만 막던) 겉감 관련 합치기 요청을 더 엄격하게** 만든다(의도된 변경).
- 테스트: e2e `서버 방어선: …`, `겉감 짝 조건 불충족: 기존 겉감이 2개면 …`, `… 새 인식 겉감이 2개면 …`, `겉감과 무관한 기존 합치기 규칙은 그대로 동작한다`; 단위 `outer-fabric-pair.util.spec.ts`(`LINING ⊄ INTERLINING` 포함).

## 합치기에서 바뀌는 칸 / 유지되는 칸 (사용자 결정: 이름 갱신 없음)
- **혼용률**: PR-246 규칙 — 비어 있으면 채움 / 같으면 불변 / 다르면 기존 유지(행 단위 `overwriteComposition:true` 명시 시에만 교체) / 들어온 값이 비면 절대 지우지 않음(`resolveCompositionUpdate`).
- **유지**: 자재명·구분·요척·필요량·색상·규격·단가·수동 값·확정 값, 새 Item 생성 없음.
- **알아둘 점(보고서의 "혼용률만"보다 넓음)**: 겉감 짝 합치기도 기존 합치기·same 갱신과 **같은 공용 처리**(`applyIncomingToExistingBomItem`)를 타므로, 들어온 행이 유효한 작지 수량(`sheetQty`>0)을 가지고 있으면 **`sheetQty`/`sheetQtyUnit`(작지 원본 출고량 참고 값)도 갱신**되고, 요척·필요량이 다르면 "자동 반영하지 않음" 알림(`BOM_ITEM_VALUE_DIFF`)만 남는다(값은 안 바뀜). 이는 기존 합치기 동작 그대로이며 이 PR 이 새로 만든 것이 아니다.
- 발주·입고·선적 연결 행 보호(PR-235): 합치기는 행을 삭제하거나 이름을 바꾸지 않아 연결에 영향이 없고, 삭제 보호 로직(`decisions.existing` 처리)은 변경 없음.
